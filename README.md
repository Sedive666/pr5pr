# Практическая работа 4. Подключение REST API

Магазин кроссовок на Flutter Web. Продолжение ПР3: хранилище в памяти заменено
настоящим сервером. Данные приходят по HTTP через Dio, сетевые ошибки
превращаются в исключения предметной области, поиск, фильтрация, сортировка и
постраничный вывод выполняются на сервере.

Экраны и формы из ПР3 не изменились: поменялась только реализация
`EntityRepository`.

## Запуск

Сервер (Node.js 18 или новее, зависимостей нет):

```bash
node api/mock-server.js --port 8080 --origin http://localhost:5555
```

Клиент — только с фиксированным портом, иначе источник запроса меняется при
каждом запуске и сервер начинает отклонять запросы:

```bash
flutter pub get
flutter run -d chrome --web-port=5555
```

Перед запуском клиента сервер должен отвечать на `http://localhost:8080/api/__health`.

Адрес сервера задаётся параметром сборки, а не константой:

```bash
flutter run -d chrome --web-port=5555 --dart-define=API_BASE_URL=http://192.168.1.10:8080/api
```

Проверки:

```bash
flutter analyze
flutter test
```

## Слои

```
screens → widgets → state (ListNotifier, provider) → repositories → core (Dio) → сервер
```

| Слой | Содержимое |
| --- | --- |
| `core` | `config.dart` — адрес и таймауты; `api_client.dart` — Dio, интерсептор, повтор; `api_exceptions.dart` — исключения предметной области |
| `models` | сущности с `toJson`/`fromJson`, `PageResult<T>`, условия отбора, валидаторы |
| `repositories` | `EntityRepository<T, Q>` и единственная реализация `ApiRepository<T, Q>` |
| `state` | `ListNotifier<T, Q>` — загрузка, четыре состояния, выделение, сохранение, удаление |
| `widgets` | `EntityTable<T>`, `EntityCardList<T>`, `EntityListView<T, Q>`, `EntityFormScreen` |
| `screens` | экраны сущностей: только описание колонок и полей формы |
| `api` | учебный сервер `mock-server.js` и контракт `КОНТРАКТ-API.md` |

Виджеты не знают о существовании Dio: наружу из репозитория выходят только
наследники `ApiException`.

## Эндпоинты

Единообразный набор операций доступен для `sneakers`, `brands`, `series`,
`categories`, `customers`, `orders`, `reviews`.

| Запрос | Назначение |
| --- | --- |
| `GET /api/sneakers` | список с поиском, фильтрами, сортировкой и страницами |
| `GET /api/sneakers/{id}` | одна запись, `404` если не найдена |
| `POST /api/sneakers` | создание, ответ `201` |
| `PUT /api/sneakers/{id}` | изменение |
| `DELETE /api/sneakers/{id}` | логическое удаление, ответ `204` |
| `DELETE /api/sneakers/{id}?hard=true` | физическое удаление |
| `POST /api/sneakers/{id}/restore` | восстановление |
| `POST /api/sneakers/bulk-delete` | множественное удаление, `{deleted: N}` |
| `GET /api/__health` | проверка живости |
| `POST /api/__reset` | восстановление начального набора данных |

Параметры списка: `search`, идентификаторы связей (`brandId`, `seriesId`,
`categoryId`, `customerId`, `status`, `rating`, `city`), `yearFrom`, `yearTo`,
`sort` вида `price,desc`, `page`, `size`, `includeDeleted`.

Полное описание — в [api/КОНТРАКТ-API.md](api/КОНТРАКТ-API.md).

## Обработка ошибок

| Ответ сервера | Исключение | Что видит пользователь |
| --- | --- | --- |
| нет ответа, таймаут, CORS | `NetworkException` | состояние ошибки с подсказкой и кнопкой «Повторить» |
| `401` / `403` | `UnauthorizedException` / `ForbiddenException` | сообщение о входе или правах |
| `404` | `NotFoundException` | запись не найдена, `findById` возвращает `null` |
| `409` | `ConflictException` | сообщение о конфликте внизу экрана |
| `422` | `ValidationException` | ошибки под соответствующими полями формы |
| `5xx` | `ServerException` | состояние ошибки с кнопкой «Повторить» |

Коды `4xx` пропускаются через `validateStatus` в обычную ветку ответа и
разбираются интерсептором: он отправляет их по ветке ошибок сам, приложив
готовое исключение. Иначе Dio завернул бы его в `DioException` с типом
`unknown`, и обработчик `on ValidationException` не сработал бы.

Ключи объекта `errors` в ответе `422` совпадают с именами полей модели,
поэтому `EntityFormScreen` раскладывает серверные ошибки по полям формы.

Код `409` сервер возвращает в двух случаях: удаление записи, на которую
ссылаются другие, и заказ модели, у которой не осталось свободных пар.

## Сетевой слой

- базовый адрес через `--dart-define`, таймауты 10 с на соединение и 15 с на ответ;
- интерсептор в режиме отладки печатает метод, адрес и код ответа каждого запроса;
- устаревшие запросы списка отменяются через `CancelToken`: при быстром вводе
  в поиск ответ на короткую строку не может перезаписать ответ на длинную;
- чтение повторяется при сетевом сбое — до трёх попыток с нарастающей паузой,
  записи не повторяются никогда;
- справочники для выпадающих списков запрашиваются один раз, кэш сбрасывается
  при любой записи в репозиторий;
- кнопка сохранения заблокирована на время отправки.

## CORS

Браузер не отдаст ответ коду приложения, если сервер не разрешил источник явно.
Со стороны Dart ошибка CORS неотличима от выключенного сервера — тип исключения
одинаковый, `connectionError`, поэтому в тексте `NetworkException` есть прямая
подсказка посмотреть консоль браузера.

Сервер добавляет ко всем ответам `Access-Control-Allow-Origin` с адресом
клиента, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` и
отдельно обрабатывает предварительный запрос `OPTIONS` с ответом `204`.
Без обработки `OPTIONS` чтение работает, а запросы с телом — нет.

## Учебные переключатели

| Параметр | Действие |
| --- | --- |
| `/sneakers?__delay=1500` | задержка ответа сервера — проверка индикатора загрузки |
| `/sneakers?fail=1` | запрос уходит с `__fail=500` — проверка состояния ошибки |
| `POST /api/__reset` | возврат данных в исходное состояние |

## Проверки полей

Клиент проверяет формат и диапазоны, сервер — то, что клиенту недоступно.

| Поле | Проверка на клиенте | Проверка на сервере |
| --- | --- | --- |
| Название модели, бренда, линейки, категории | обязательно, длина | — |
| Артикул | 4–20 латинских букв, цифр и дефисов | уникальность |
| Почта | формат | уникальность |
| Номер заказа | длина | уникальность |
| Бренд, линейки, категории, покупатель, модель | выбор обязателен | существование записи |
| Доступно пар | не больше общего количества | то же |
| Заказ модели без свободных пар | — | конфликт `409` |

## Тесты

`test/repository_test.dart` — репозиторий с подменённым транспортом Dio:
сетевых запросов нет, ответ задаёт тест, интерсепторы работают по-настоящему.
Проверяются разбор оболочки списка, передача условий отбора в параметры
запроса, `422` → `ValidationException` с ключами полей, `409` →
`ConflictException`, недоступность сервера → `NetworkException` вместе с
числом повторов, `404` → пустой результат, работа кэша справочников.

`test/fake_api.dart` — мини-сервер в памяти для виджет-тестов;
`test/query_test.dart` — экраны и формы поверх него; `test/model_test.dart` —
разбор JSON.
